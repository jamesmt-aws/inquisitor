# S1: deletion-minimality (design pair)

Inputs: `design-pre.md`, `design-post.md`, plus preferences preamble. The post-state is the result of a change the team labeled in its commit message as a simplification. Treat each named Procedure and each numbered Property in design-pre as a unit.

For each Procedure or Property in design-pre **not present in design-post**, classify:

(a) the unit was deleted; the input case it covered is no longer handled. Cite the input case.
(b) the unit was absorbed into another procedure or property in design-post. Cite which.
(c) the unit was relocated to data, types, state, dispatch, action representation, module structure, or a richer cost function. Cite where.
(d) the unit was redundant with another unit already in design-pre. Cite which.

For each Procedure or Property in design-post **not present in design-pre**, classify:

(a) introduced because the change exposed a distinction the preferences require.
(b) introduced as accidental complexity; the preferences do not reward it.

**Verdict for S1.** Does the post-design represent a deletion-minimal move from pre under the stated preferences?
- `improved` requires removals that fall into (b)/(c)/(d), or (a) removals whose input case the preferences do not reward, plus any post-(a) additions for input cases the preferences require.
- `regressed` if removals lose preference value, or post-(b) additions appear.
- `unchanged` if removals and additions cancel.

Cite one line per classification.
