# S3: MDL compression (path cost plus artifact complexity)

Inputs: a design document, the code that implements it, and a test suite the code passes.

Take two measurements.

**Path cost.** Generate the code from the design under the test suite (a capable model produces an implementation, which is checked against the suite). Report the token count for that generation. Then generate the design from the code (the same model summarizes the code into a design at the same resolution as the input design). Report that token count too. The two numbers estimate K(code | design) and K(design | code) respectively. Holding the test suite fixed across the comparison keeps correctness constant; any difference in path cost reflects how much the design constrains the code.

**Artifact complexity.** Report a simple complexity measure for each artifact in isolation: gzip size, line count, or McCabe. The same measure for both artifacts in the pair.

Place the (design, code) pair in one of four cells:

| | simple artifact | complex artifact |
|---|---|---|
| low path cost | design earned its keep on a simple result | design earned its keep on a large result (a grammar producing a parser) |
| high path cost | design did not constrain; the answer happened to be simple | design did not help; output is messy |

**Verdict for S3.** Report the cell. The third and fourth cells are flags. The fourth is the strongest flag; the third is a softer flag (the design did not help even though the code is fine).

Notes. Path-cost estimates are model-relative; record the model used. Memorization is a confound for public codebases the model has seen; private code or held-out forks suppress it. For Pareto-loop comparisons inside a fixed codebase, the same memorization confound applies to both candidates and partially cancels.
