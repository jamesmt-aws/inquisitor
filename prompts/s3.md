# S3: MDL compression (design + code at both ends)

Inputs: `design-pre.md`, `before/` (code), `design-post.md`, `after/` (code).

Compute byte counts (file-size approximation):

- `|design_pre|`, `|code_pre|`, `|design_post|`, `|code_post|`.

Estimate qualitatively how predictable the code is given its design. A sharp design (concrete types, named structural commitments, explicit invariants) implies a tight implementation distribution; a vague design implies diffuse. Score each side on a 1-5 scale, with a one-line citation.

Compare:

- For pre: does `|design_pre| + cost(code | design_pre)` come in below `|code_pre|`? Use the predictability score as a proxy for the conditional cost; lower predictability means higher conditional cost.
- For post: same comparison.

Did the change reduce total description length on either side? Did any new structure introduced (new file, new type, new abstraction) earn its keep against what it absorbs (a runtime guard, a parse-time helper, a maintenance comment, an unreachable case, a dead field)?

**Verdict for S3.** `improved` / `unchanged` / `regressed`, with one-line citation per claim.

Note: byte counts are coarse when the touched-file scope is much larger than the substantive change. If S3 is asked to discriminate finer-grained simplifications, restrict the byte sum to files where substantive change occurred and report both totals.
