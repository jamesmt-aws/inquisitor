Code grew by 928 bytes. Design shrank by 510 bytes.

## Predictability of code given design

**Pre.** Score: 3 / 5. The design names the procedures and their map-iteration shape, but the design does not say *why* the map cardinality is bounded at one. A reader regenerating code from the pre-design would plausibly write a multi-variable cross-product implementation, since the type and the iteration shape both admit it. The constraint that "the map always has exactly one entry" lives in the design's parsing-procedure prose and the runtime guard, not in the data shape. The hasPerItemGate shadowing is invisible from the design alone.

**Post.** Score: 4 / 5. The design states `*ForEachBinding` and its two fields. A regenerating implementer would not produce a map; the type forecloses it. The init-time assertion is named explicitly. `hasPerItemGate` computed once per function is an obvious property at this resolution. Remaining unpredictability sits in the YAML-shape parsing detail and the per-item carry-forward logic, both of which are design-level prose neither version eliminates.

## MDL comparison

`|design_pre| + cost(code | design_pre) ≷ |code_pre|`. With predictability 3/5, the conditional cost stays high relative to a sharper design; the design earns roughly its own bytes back but not much more. Pre-state design is paying for itself, not earning extra compression.

`|design_post| + cost(code | design_post) ≷ |code_post|`. With predictability 4/5, the conditional cost drops; the post-design's named structures (`*ForEachBinding`, `_nodeStateCount`, `init()` assertion) compress the code more efficiently than the pre-design's procedural prose did. Post-state design earns its keep more clearly.

## Net effect

Total `|design| + |code|` shrank by 510 + (-928) = grew by 418 bytes if we treat the two as additive. But MDL is not the file-size sum; it asks whether the lower-resolution description compresses the higher-resolution one, and the post-design compresses better per byte. The 928-byte code growth is in the form of the `init()` block, the `_nodeStateCount` sentinel, the `*ForEachBinding` struct definition, and the inline cardinality validation in two parser branches. Each of those carries a structural commitment the pre-design discharged via comments and runtime guards. The new structure earns its keep against what it absorbs (a parse-time helper, a runtime cardinality check, a code-comment maintenance obligation, a redundant gate computation, a dead field).

## Verdict

**S3 improved.** Code grew slightly; design shrank; predictability of code given design rose from 3/5 to 4/5. The added structure absorbs distinctions that previously lived in prose or runtime checks. New structure pays its keep.

Citation: `*ForEachBinding` (≈10 lines new struct + 6 call-site simplifications) and `_nodeStateCount` + `init()` (≈12 new lines) absorb a runtime guard, a parse-time helper, a maintenance comment, and an unreachable iteration shape.
