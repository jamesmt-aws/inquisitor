# S2: partition match (PR #228)

## Input partition

- Same node processed: once / twice in a single walk (skip-then-dispatch).
- forEach: N items / N−1 / N→0.
- Prune: candidate has stale key / has fresh key / has no entry.

## Branching partition (pre)

- Tracking shape cell: append to flat slice.
- Per-node entry cell: not distinguished — same node's two contributions live as separate slice entries.
- Prune cell: scans flat slice; cannot tell which entry came from which writer.

## Branching partition (post)

- Tracking shape cell: write to per-node map entry.
- Per-node entry cell: distinguished by map key; last writer wins.
- Prune cell: scans flattened map values; one entry per node.

## Cells in pre's branching partition not in post's

- **Two-contributions-per-node cell.** Classification: **(b) deleted**. The input case "same node contributes twice in a walk" no longer exists by construction; the map shape forecloses it.

## Cells in post's branching partition not in pre's

- **Per-node uniqueness cell.** Classification: **(a) preferences require this distinction**. Correctness rewards the invariant that pruning sees the latest applied set per node, not an accumulation across writers.

## Verdict

**S2 improved.** Pre's branching partition was coarser-than-required along the per-node axis (it could not distinguish multiple writes to the same node). Post adds the distinction the preferences require, and forecloses the failure case via map semantics.

Same conflation note as S1: this is a bug fix that takes the shape of a partition-match move.

Citation: pre's two-contributions cell collapses via type relocation; post's per-node cell satisfies a preference-required input case.
