## Predictability of code given design

**Pre.** Score: 2 / 5. Pre-design does not name the owner-Graph race; a regenerator following pre-design produces code that has the race. The wrong ordering is also a property of pre-design, so a regenerator reproduces it.

**Post.** Score: 4 / 5. Post-design names `ownerDeleting()`, the patch-finalizer composition, and the corrected ordering. A regenerator produces code with the right behavior and the right ordering.

## MDL comparison

The compression move here is non-trivial. The post-design adds three structural commitments (trigger surface, blocking composition, ordering rule). Each adds bytes to the design but absorbs cases the pre-state code would have had to handle ad-hoc (and got wrong). The "no new API" claim itself is an MDL signal: the change adds capability without expanding the primitives surface, which means downstream users do not need to learn new vocabulary.

Net bytes grew on both sides. The MDL win is partial: design absorbs ad-hoc handling for two cases, but at the cost of explicit description.

## Verdict

**S3 unchanged.** Code grew (mostly tests, some production); design grew correspondingly; predictability rose from 2 to 4. The "no new API" composition is a real MDL improvement at the primitives level (no new vocabulary), but the code-and-design-bytes growth offsets it at the file-size level.

S3 is on the border between unchanged and improved here. I'm calling it unchanged because bytes grew on both sides and the predictability rise is largely about adding explicit handling rather than absorbing existing prose into structure.
