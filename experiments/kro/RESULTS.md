# Experimental results: simplicity metrics on the kro corpus

We tried to detect complexity in code by back-calculating designs from it and asking which parts felt simple enough relative to predefined criteria. For each change in the corpus, an LLM read the touched Go files at both the before-state and after-state, producing a design document at each end: a one-paragraph purpose, a list of named procedures, and ten or so testable properties. The criteria came from a list of preferences we wrote in [`prompts/preferences.md`](../../prompts/preferences.md): correctness, observable behavior (status conditions, events), and public API stability (CRD fields and DSL surface). These are minimal behaviors most reconcilers should agree to, a baseline we wrote ourselves. The corpus: 232 commits over two months on Ellis Tarn's fork of kro, all his work. We focused on 11 PRs in detail: 7 Ellis tagged as simplifications in his commit messages, plus 4 we picked as controls of similar diff size (feature adds and bug fixes).

We ran three prompts on each pair of designs. The first asks which design units could be deleted without violating any preference. The second asks whether the design distinguishes exactly the cases the preferences require. The third asks whether the design serves as a useful summary of the code, where a reader could reproduce the code from it alone. Each prompt returns improved, unchanged, or regressed, plus a one-sentence citation pointing at specific design elements. Good output names specific units and the preferences they serve or violate. Bad output hand-waves, invents design sections, or marks code the preferences need as deletable. Separately, we identified 12 PRs where Ellis added machinery and then in a later PR removed it (we called these "regret pairs"), and ran Ellis's existing Go static-analysis tool plus its audit prompt on the same code so we could compare.

Tenets came out of Ellis's commit history. The team encodes its commitments in the commits themselves; we pulled out eight that read directly off them: "correctness over performance," "one name per concept," and so on. Each tenet shows up many times. "One name per concept" appears as eight separate rename commits across the corpus. "Correctness over performance" appears in 15 bug fixes that walked back optimization-layer races. We named patterns the history was already showing us. The forward-looking detector flags any tenet that conflicts in practice with a higher-priority tenet (for instance, performance optimizations producing correctness bugs) when those bugs accumulate faster than the underlying conflict is being resolved. On the kro corpus retrospectively, the detector would have flagged the performance tenet about 15 days before Ellis actually demoted it at #244. On one commit specifically (#220, where Ellis split a file the wrong way and walked the split back later in #261), our prompts caught the mistake from the design alone; Ellis's audit would have justified the original split because his audit demands a design citation, and design 005 of that period covered mechanism only.

The verdicts from S1/S2/S3 depend entirely on the preferences you give them. Under a minimal preference set, the metrics mark every optimization as deletable. Under the preferences active at the time of the commit, every addition is judged necessary. The one C1/C2/C3 comparison we ran was on a pair of states (#190 vs #245) where Ellis had already decided that #245 was simpler, so the verdict was predetermined. Compared to Ellis's audit, our framework does a similar job with less machinery. Our prompts catch cases where the design tells the implementer to do more than the preferences require. His audit catches cases where the code itself is too tangled (800-line functions, types doing several unrelated jobs). Our prompts cover non-Go codebases and design-only review. Where both methods run, they are complementary.

The single biggest threat to the analysis is being wrong about the tenets, so the most important next step is asking Ellis to read the eight we derived and tell us whether they match what he has actually been doing. Three more steps after that. First, calibrate the shift detector's threshold (how many fixes against a tenet, over what window, before flagging) so the rule applies without per-project tuning. Second, apply the framework prospectively at PR time on a live project, to see whether it surfaces issues the team agrees with before a strip cascade arrives. Third, formalize the tenet-derivation step as a reproducible procedure: a prompt or script that produces a candidate tenet list from any commit history.
